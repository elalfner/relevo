# Updating an existing issue

`go` builds exactly what an issue says, so its text is only free to change while Relevo has not committed to a build. The mode is the issue number in `$ARGUMENTS`; you edit the description only, never the title, labels, milestone or assignee.

1. **Read it.** `node ${CLAUDE_PLUGIN_ROOT}/scripts/tracker.mjs issue-get <n> --fields number,title,body,state,labels > <file>` (the file goes outside the working tree). If the issue does not exist, say so and stop.
2. **Ask whether it may be edited.** `node ${CLAUDE_PLUGIN_ROOT}/scripts/can-edit-issue.mjs --input <file>`. Exit 0 prints `editable`. Exit 3 prints `withdrawable`: the issue is `ready` with no `go` label, so its text is approved. Say so and ask whether to withdraw the approval to edit it (an edit would withdraw it anyway before any build, because the text that is built is the text that was approved). On a clear yes, remove `ready` with `node ${CLAUDE_PLUGIN_ROOT}/scripts/tracker.mjs state-set <n> --remove <the ready label>`, remember that the approval was withdrawn, and go on. Otherwise change nothing. Exit 1 prints the label found and why: change nothing and tell the person that the text is what `go` builds and name the label. If the label is `go`, a build was requested for this text: wait for the cloud to decide, then edit. If `building` is the label, they must wait for the build to finish or fail first. Only an open issue with no lifecycle label, or with `needs-spec` alone, is editable, once a `ready` with no `go` has been withdrawn.
3. **Start from the current body.** Ask only what the person wants to change, keep every part they did not mention, and do not invent scenarios or edge cases. An existing `## Documentation` section stays exactly as it is unless the person asks to change it; it still carries only glossary entries and decision records.
4. **Recheck the dependencies.** Every `Depends-on: #N` in the new body must name an existing issue (`node ${CLAUDE_PLUGIN_ROOT}/scripts/tracker.mjs issue-get N --fields number`) other than this one, and every `Depends-on: owner/repo#N` an existing issue of a linked repository (`node ${CLAUDE_PLUGIN_ROOT}/scripts/tracker.mjs issue-get N --fields number --repo owner/repo`). Fix a missing or self-referencing line with the person before going on.
5. **Check.** Save the new body outside the working tree and run `check-issue.mjs --title "<current title>" --body-file <file> --platforms <names> --links <links> --rules-file <qa.rules_from>`; an update keeps the `Platform:` line unless the person changes it. Fix every problem with the person; apply nothing while it fails. Show the warnings about protected paths and unconfirmed names and ask how to proceed, as in step 4 of the creation flow.
6. **Approve.** Show the new text next to the current one, the `Documentation` section whole, and ask for explicit approval. If the person asks for more changes, revise, check and show it again. Apply nothing before a clear yes.
7. **Apply.** Read the issue again with `node ${CLAUDE_PLUGIN_ROOT}/scripts/tracker.mjs issue-get <n> --fields state,labels` and run `can-edit-issue.mjs` on it. If it is no longer editable, apply nothing and explain the refusal as above. Otherwise `node ${CLAUDE_PLUGIN_ROOT}/scripts/tracker.mjs issue-edit-body <n> --body-file <file>`, never in the same command as a label: the approval offered next must come after the edit. Then print the issue link.
8. **Offer the approval for a `needs-spec` issue, or one whose approval was withdrawn.** Only then, ask the same question of three answers as step 7 of `SKILL.md` for #<n>: nothing, `ready`, or `ready` and `go` (with its rules: `go` only where the cloud can build, permission, nothing without a clear choice). Approving starts nothing. On `ready`, take the changes from `node ${CLAUDE_PLUGIN_ROOT}/scripts/label-change.mjs --to ready --current "<the labels>"` and apply them with `node ${CLAUDE_PLUGIN_ROOT}/scripts/tracker.mjs state-set <n> --add <names> --remove <names>` (for `needs-spec` that swaps it for `ready`). On `ready` and `go`, then apply `go` in a command of its own. On nothing, leave the labels as they are and remind that the issue is built only after it is approved with `ready`.
