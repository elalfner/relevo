# Design

## Context

See proposal.md. Both issues touch the check of a draft (`scripts/lib/issue-check.mjs`), the build preflight (`scripts/lib/build-preflight.mjs`), `skills/issue/SKILL.md` and the hand-off. #121 (merged) already gave the pieces to reuse: `build-preflight.mjs` has the `changedPaths(line)` reader of "a verb that changes something, then a path" and `checkSpecStage`, which stops a task that changes a protected path; `protected-paths.mjs` is the single decision of what is protected; the `notes` of the preflight reach the hand-off as `check: ...` on the "Inputs to confirm" line; and `rule-conflicts.mjs` and `check-issue.mjs` show the shape of a lexical check that quotes the lines it relies on.

Observed in the code, not assumed:

- The hard guard at commit time (`commit-change.mjs`) ends a run with the reason `protected path in the diff`. `messages.mjs` builds the `qa_failed` line `QA still rejected it after the retries (protected path in the diff)` for every reason that is not a limit, so a refused path is reported as a QA verdict. The state is `unsafe`, so the next step is `rebuild` (build again on your machine), which does not help: the issue must change.
- The next-step text of `needs-spec` with `policy` says "list the dependency manifest in `Allow-paths:`, or change the issue so that it does not need the protected path". For the rules file or a workflow the first half is wrong (the check refuses such an `Allow-paths:` entry). The `policy` reason is produced by `build-preflight.mjs --stage spec`, by the `finding_class` of a QA finding, and (the #121 note) by a specification agent that sends back an issue for a project rule.
- `checkIssueDraft` already refuses an `Allow-paths:` entry that can never be allowed, with a message that says why.
- The `Assumptions` of the issue are copied to `design.md` as `## From the issue: Assumptions`, and the specification agent writes its own `Assumptions` heading there.
- The `built` message has `risk` and `inputs_to_confirm` lines; it has no line for either of the new facts.

## Goals / Non-Goals

**Goals:** tell the writer about protected paths and unconfirmed external names while the issue is written; make a refused protected path read as a policy; make the hand-off show assumed names and shared code; keep every verdict reproducible from a script (#119 C1, #122 C1).

**Non-Goals:** letting an unattended run edit protected paths; blocking changes to shared code; stopping a build because of an assumption; changing a guard, the validation gate, the test-run script or `qa-run.md` (#124 runs in parallel); a `relevo.yml` setting for the shared folders.

## Decisions

- **D1. One change for both issues.** They edit the same four places, and a second change would conflict with the first in `issue-check.mjs` and `skills/issue/SKILL.md`.
- **D2. The draft warning reuses the build reader and the guard.** A new `scripts/lib/protected-mentions.mjs` walks the body line by line (outside fenced code and the sections `Out of scope`, `Code pointers`, `Design reference` and `External inputs`, and skipping a line with a negation before the verb), takes `changedPaths(line)` for a line that asks for a change, and `checkProtected` / `hardRule` for the decision. A path of a line with no verb is reported only when it is hard-protected ("warn, do not block" for the rules file named in prose); a manifest is reported only with a verb, because issues name `package.json` to say what the project uses. All of it is a warning: the person decides, and the spec stage still stops a task that changes the path. Alternatives: block in `check-issue` (rejected: a lexical read of prose has false positives, and the issue says "warn, do not block"); ask a model (rejected by #119 C1). The restricted files are not included: the issue lists the rules file, workflows, `relevo.yml`, skills and manifests, and the spec stage already covers restricted ones.
- **D3. The wording is fixed where it is wrong, not with a new reason.** `messages.mjs` gets a small table from the reason of a failure to a policy `happened` line, with one entry, `protected path in the diff`, and a `qa-failed` next-step reason `protected` (`/relevo:issue {n}`, spec writer). It is chosen when `recovery` and a finding class do not decide. The `policy` hints of `needs-spec` and `qa-failed` are rewritten to be true for the rules file and for a manifest. The other refusals of the commit guard (`restricted file in the diff`, `outside the platform`, credential) have the same wording problem but are not in #119, so they are left as they are and the table makes adding them a one-line change. `needs-spec` keeps the reason `policy` (the workflow, the digest and `progress.mjs class` know it). Whether a specification agent that rejects an issue "for a rule" should use `policy`: the scripts produce `policy` only for protected paths and dependencies, so a rule conflict has its own reason (`conflict`, #121); the hint fix removes the misleading text for the cases that do use `policy`. No change in `skills/go/SKILL.md` for it.
- **D4. An external name is a backticked name next to a word of an outside kind, settled by the repository.** `scripts/lib/assumptions.mjs` reads the bullets of an `Assumptions` section. A bullet is about something outside when it has a word of that kind (permission, scope, role, endpoint, route, field, property, claim, header, contract, backend, server, schema, enum, flag, in English and Spanish) and a backticked name that is not a path of the repository. Each name is searched with `git grep -F` in the tracked files outside `openspec/`; found means "the repository holds it" and the assumption is dropped, with the file kept in the output so a person can see why. Finding a name proves that the repository mentions it, not that the backend has it, so the output says "found in <file>". An assumption with that kind of word and no backticked name cannot be settled and stays. Without a git repository nothing is found, so everything stays (fail towards listing).
- **D5. The build proceeds; waiting is the writer's choice.** #122 allows either. A lexical match that stops a build would be wrong in the cases #121 measured, so the build never stops for an assumption: the spec stage lists it as `assumed`, and the hand-off puts it at the top. A writer who wants the build to wait writes an open question, which `check-issue` already refuses to build; the draft warning offers that as the third way out, beside "confirm now" and "keep as a `manual` external input".
- **D6. Where the spec stage reads them.** `build-preflight.mjs --stage spec` reads `design.md` for the headings `Assumptions` and `From the issue: Assumptions`. It adds `assumptions` and `assumed` to its output and leaves the decision alone. `go` runs it before the developer and again at the hand-off (step 7, with the same arguments), so it does not carry the list across the build. The issue stage is not changed: the draft check already warned about the same bullets.
- **D7. Shared code is a script of the diff and the import graph.** `scripts/lib/shared-code.mjs` takes the list of changed files with their status, the list of tracked files and a reader of their text, and returns the shared ones. A file is shared when it matches a shared-folder rule (`components`, `shared`, `common`, `composables`, `core`, `ui`, `widgets` as a folder name at any depth, or a `--shared` glob) or when more than one other tracked source file that is not a test imports it. Imports are read with regular expressions for `import ... from`, `import '...'`, `require('...')`, `import('...')` (JavaScript, TypeScript, Vue, Svelte) and `import '...'` / `export '...'` (Dart), and resolved against the tracked file list: relative paths, the aliases `@/` and `~/` (suffix `src/`), and `package:<name>/` (suffix `lib/`), with the extensions and `index` files of each family. PHP and other languages only get the path rule, and the output says so in `notes`. Counting files, not folders: screens often share one `views/` folder. The CLI `scripts/shared-code.mjs --base <branch>` reads `git diff --name-status origin/<base>...HEAD` (or `<base>...HEAD`), prints `{ shared, line, notes }` and fails open. Alternatives: a model reads the diff (rejected by #122 C1); a `relevo.yml` list of shared folders (left for later: it needs a schema change and the default rule covers the pilot's layout).
- **D8. The hand-off gets two optional lines.** `built` gets `assumed` and `shared_code`, each a line that disappears when empty, in both languages. `assumed` goes before the branch line, because the issue asks for it "at the top of the hand-off"; `shared_code` goes after `risk`. Both come from scripts: `go` copies `assumed` from the spec check and `shared_code` from `shared-code.mjs`, and does not write them itself. The `check:` notes keep their line.
- **D9. Small edits to the skills.** `skills/issue/SKILL.md` adds the two warnings to step 4 and to the External inputs paragraph; `skills/issue/references/update.md` says the update flow does the same. `skills/go/SKILL.md` gets two sentences in step 7 (the two commands and the two fields) and nothing else. `agents/dev.md` is not edited: the developer needs no new behaviour for either issue.

## Risks / Trade-offs

- A lexical read of the issue text misses a path written in a way the reader does not know and flags a line that only describes → it is a warning with the line quoted; the spec stage and the commit guard still stop the real thing (D2).
- A name found in a mock or a fixture settles an assumption that the backend does not satisfy → the output says where it was found; the hand-off and QA are unchanged for that case (D4).
- The import graph is approximate (dynamic paths, barrel files, path aliases of other bundlers) → it only adds to the list; the path rule and the diff are exact; the output notes the languages it did not read (D7).
- Many warnings can be ignored by a writer in a hurry → each names a path or a name and the three ways out, and the sections that only point are skipped to keep it short.
- A broad shared-folder rule lists files that only one screen uses → the list says why each file counts, and nothing is blocked.
