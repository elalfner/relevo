# Design

## Context

The text of an issue is checked in two places, both with no model: `checkIssueDraft` (`scripts/lib/issue-check.mjs`, used by `issue` before creating it) and `build-preflight.mjs --stage issue` (before the agent of a build). QA is decided by `qa-aggregate.mjs`: `spec`, `security` and `code` block, `interface` is advisory on the last attempt, and the report of a lens is `QA PASSED` or `QA REJECTED` with numbered findings. Nothing reads the rules file in a script today; only the `spec` lens reads it, and a lens can call a violation a note. The `qa.rules_from` setting is a list of files.

## Goals / Non-Goals

**Goals:** raise a conflict between the issue and the rules (or inside the issue) before a turn is spent; make a cited violation of a hard rule block; keep C1, so each blocking verdict is reproducible from quoted lines.

**Non-Goals:** deciding which rule wins; judging a rule semantically in a script; changing the lenses' models, the retry or the budget (the sections "The model of a retry" and the parallel launch of `qa-run.md` stay as they are); editing `agents/dev.md` or `skills/go/SKILL.md` (issue #130).

## Decisions

- **D1. The pre-build check is lexical and quotes both lines.** A script cannot judge meaning, and C1 says the verdict must be reproducible. The check finds candidate pairs by words: an `Out of scope` bullet and a rule line (or the WHEN/THEN of a scenario) conflict when the other line holds at least three quarters of the content words of the bullet and at least two of them, or all of them when the bullet has one or two content words. Generic verbs ("change", "add", "block", "let"...) are not content words. Content words drop a short list of stop words in English and Spanish and are compared by a crude stem (suffixes `s`, `es`, `ing`, `ed`, `ción`...). An exclusion of the remainder (a bullet with "other", "else", "the rest", "cualquier"...) never matches: it excludes what nothing else asks for (found when the example issue of `docs/get-started.md` was flagged by "Any other change to the home screen"). The output is the two quoted lines; a person re-reads them and decides. Alternative: ask a model, rejected as the only judge because its verdict would not be reproducible (C1); a model may still be used by `issue` and `think` to write the draft, but the blocking verdict comes from the script. The cost is false positives and misses, accepted because a false positive is solved with an override and a miss is still caught by QA (D5).
- **D2. Only a positive requirement conflicts with an exclusion.** A rule line counts when it has a requirement word (`must`, `shall`, `required`, `always`, `every`, `each`, `debe`, `siempre`, `cada`, `obligatorio`...) and has no prohibition (`must not`, `never`, `do not`, `nunca`, `no debe`...). A prohibition agrees with an exclusion. Bullets and sentences are the unit: the lines of the rules file are read one by one, with their number.
- **D3. A rule is a requirement unless it is marked `[advice]`.** The issue asks for a marker "in the rules file or a lens setting". A marker in the file keeps the exception where the rule is, in the file the project already owns, and `docs/configuration.md` says no setting lowers what a reviewer blocks. Default hard, because the rules file of the pilot says that breaking them is rejected. `[advice]` on a line marks that line; on a heading it marks every line until the next heading of the same or higher level. Alternative: a `[hard]` marker, rejected because an unmarked rules file (every existing project) would then block nothing.
- **D4. The override is a decision of the issue.** `Overrides: <file>:<line>` on a line of a `### D<n>.` block (under `Decisions`) records that the person chose the issue over that rule, with the decision's `Decided:` and `Why:` as the record. `<file>:<line>` must be a line that exists; an override that names a line that is not a rule is itself a problem of the draft. `Overrides:` outside a decision does not count. The check only skips the pair; QA still reads `design.md`'s copy of the decision, so an override lets the build proceed on the exclusion but the lenses will not reject a change for obeying it (the `spec` lens already treats a decision of the issue as binding). Alternative: a free-text waiver, rejected because it is not machine-checkable.
- **D5. A rule violation found by QA blocks through a verifiable citation.** A lens cites `Rule: <file>:<line> "<quoted text>"`. `qa-aggregate.mjs` is given `--rules-file` (the files of `qa.rules_from`) and checks that the line contains the quote (whitespace and case normalised) and is not `[advice]`. A verified citation makes the finding blocking: it moves from `advisory` to `findings` for the `interface` lens on its last attempt, and a `QA PASSED` report that contains one becomes `QA REJECTED` with a synthesized finding of class `fixable`. A citation that does not verify is listed as `unverified` and changes nothing else, so a lens cannot block by inventing a rule (C1). Without `--rules-file` nothing is verified and the aggregation behaves as before. Alternative: let every lens finding block always, rejected because the `interface` lens advisory rule of the last attempt is deliberate and applies to taste, not to written rules.
- **D6. A new reason `conflict` for `needs-spec`.** The existing reasons say "complete what is missing", "an input", or "a task needs something an unattended run may not do"; a conflict needs a different instruction (settle which wins). `next-step.mjs` and the comment follow the existing pattern; the workflow template reads the reason from the JSON and needs no change.
- **D7. The scenarios comparison is only against `Out of scope`, and it only warns.** Run on the 17 open issues of this repository with its `CLAUDE.md`, the first version (two shared words) flagged 5 issues and all were false positives; the stricter version still flagged 2 (an exclusion of a verb phrase whose object a scenario also names). The pair with a rule still blocks (the pilot case, and a rule is a stated requirement); the pair with a scenario is a warning in `check-issue.mjs` and a `notes` entry in the preflight, never a stop. The issue says "the scope of an issue forbids a change that one of its scenarios needs". Free-form scope statements in a summary are not parsed; only the section whose purpose is to exclude things. The finding says which scenario (its position among the complete WHEN/THEN pairs, and the `WHEN` text) and which `Out of scope` line.
- **D8. Where the code lives.** A new `scripts/lib/rules-file.mjs` reads a rules file into `{ file, line, text, advice }` entries; a new `scripts/lib/rule-conflicts.mjs` finds the pairs. `issue-check.mjs` and `build-preflight.mjs` call it with a short block each, so #119 can edit `issue-check.mjs` without a conflict. `checkIssueDraft` gets an optional `rules` argument (the entries); `check-issue.mjs` reads the files of `--rules-file` (it already receives them) with `guarded-fs`.

- **D9. The notes of the preflight use the existing hand-off line.** `go` fills the `built` message from the environment variable `RELEVO_INPUTS_TO_CONFIRM`; the workflow adds the notes to it as `check: <note>` instead of a new variable and field, so `skills/go/SKILL.md` (issue #130) is not edited. The label says "Inputs to confirm", which is a loose fit for a note; a dedicated line is a follow-up once #130 is merged.

## Risks / Trade-offs

- A lexical check misses a paraphrase and can flag two lines that only share words → each finding quotes both lines and an override clears it; QA (D5) and the human review stay in force.
- A project that never marks `[advice]` blocks on any cited rule → that is the stated contract of the rules file; `docs/configuration.md` explains the marker.
- A lens that does not write the `Rule:` line keeps the old behaviour for that finding → the lens agents are told the format and the tests check the wording; a `spec`-lens rejection still blocks as before.
- The `Out of scope` lines that point to another issue ("covered by #130") still conflict with a rule that requires the thing → intended: the person settles it or records the override.
