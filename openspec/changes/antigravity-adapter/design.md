## Context

**What the research found.** Items marked *unverified* were not confirmed in a primary source; the first task group checks them on a real installation and stops the change if one is false. Pages read on 2026-10-21.

- **Antigravity skills** ([skills](https://antigravity.google/docs/skills)): a folder with `SKILL.md`; frontmatter has `name` (optional, lowercase letters and hyphens) and `description` (required); workspace path `.agents/skills/<folder>/` (the older `.agent/skills/` still works); global `~/.gemini/config/skills/` for the App and the IDE, `~/.gemini/antigravity-cli/skills/` for the CLI. Optional `scripts/`, `references/`. The agent loads a skill by its description; a person starts one with `/<skill-name>`. No documented key keeps a skill from being chosen by the model.
- **Antigravity subagents** ([subagents](https://antigravity.google/docs/subagents/)): Markdown with frontmatter in `.agents/agents/<name>.md` (workspace) and `~/.gemini/config/agents/` (global). Fields: `name`, `description`, `tools` (explicit list, empty by default; a misspelled tool name can hang the subagent), `model` (`inherit`, `flash`, `pro`), `commandExecutionPolicy` (`off`, `auto`, `eager`, `sandbox`; default `sandbox`), `subagent`, `mainAgent`, `mcpServers`, `skills`. No turn field is documented. The parent calls `invoke_subagent`, the subagent does not inherit the conversation, inherits the parent's allowed command prefixes, and nesting is capped at 10.
- **Antigravity rules** ([rules](https://antigravity.google/docs/rules/)): `AGENTS.md`, `GEMINI.md` or `.agents/rules/*.md` per directory; global in `~/.gemini/`. Not used by this change except to note that `AGENTS.md` and `GEMINI.md` are protected.
- **Workflows are over.** `.agent/workflows/` stopped being indexed after 2026-10-19, and skills replace them, with the same `/<name>` invocation ([migration](https://antigravity.google/docs/migration/workflows-to-skills/)). The OpenSpec 1.3.1 installed here still writes its Antigravity commands to `.agent/workflows/opsx-*.md`, so they no longer work as commands.
- **Headless CLI** ([headless](https://antigravity.google/docs/cli/headless/)): `agy -p "<prompt>"`, `--output-format text|json|stream-json`, `--print-timeout` (default 5m), `--sandbox`, `--dangerously-skip-permissions`. A tool that needs an approval nobody can give is soft-denied: the run continues, exits 0 and writes a notice to stderr. JSON output reports `status`, `num_turns` and token `usage`. No flag caps turns or cost.
- **Permissions** ([permissions](https://antigravity.google/docs/permissions?tab=cli)): rules `action(target)` in `deny`, `ask` and `allow`, evaluated Deny > Ask > Allow; actions `read_file`, `write_file`, `read_url`, `execute_url`, `command`, `mcp`; the CLI file is `~/.gemini/antigravity-cli/settings.json`; a workspace-level file is not documented for the CLI, which is what we want for a runner (the repository cannot loosen it).
- **Authentication for CI** ([authenticate](https://antigravity.google/docs/install/)): `"modelProvider": "gemini"` in the user settings plus the environment variable `GEMINI_API_KEY` ("intended for headless and CI runs"; `GOOGLE_API_KEY` and `.env` are ignored), or Application Default Credentials with `AGY_ADC_AUTH=true`. Service account keys and Workload Identity are not described for the CLI, so a keyless run is *unverified*. The feature request for API-key support ([#78](https://github.com/google-antigravity/antigravity-cli/issues/78)) was closed on 2026-09-21; its thread still carries a maintainer saying the key is "not currently supported", so the page above and a real run decide.
- **Known defect**: `agy -p` printing nothing and only ending at `--print-timeout` when there is no terminal, reproduced on 1.2.0 and 1.2.3 after the issue was closed as obsolete ([#318](https://github.com/google-antigravity/antigravity-cli/issues/318)). The run therefore always needs an outer timeout, and the first task checks the version we pin.
- **Gemini CLI** is not used here: its pages say it was replaced by Antigravity CLI for unpaid and Google One users on 2026-06-18, so building the first adapter on it would build on a product being retired for part of the audience. Its cloud action (`run-gemini-cli`) does document `tools.core` and `model.maxSessionTurns`, which is why it stays the fallback if the `agy` cloud run fails the tasks below.
- **OpenSpec as reference** (`@fission-ai/openspec` 1.3.1, `dist/core/command-generation`): a tool-agnostic `CommandContent` plus a small adapter per tool (`getFilePath`, `formatFile`). We take the shape. Relevo also needs subagents, a manifest, a run guard and a security story, so nothing is copied.

**What in `skills/` and `agents/` is neutral.** The bodies are English prose plus calls to `node ${CLAUDE_PLUGIN_ROOT}/scripts/<x>.mjs`, `gh` and `git`. The ties to Claude Code are: the frontmatter keys (`disable-model-invocation`, `argument-hint`, `model`, `effort`, `disallowedTools`); `${CLAUDE_PLUGIN_ROOT}` (about 90 uses); `$ARGUMENTS`; the names `relevo:dev` and `relevo:qa` with the verb "launch the agent" (`go`, `fix`, `review`); the `/relevo:` prefix in text; and `Task` in the workflow's tool list.

## Goals / Non-Goals

**Goals:**
- One source, one renderer per tool, the first for Antigravity, so a person can run Relevo from the IDE, the App or the CLI.
- `relevo init` asks tools and scope; what it writes can be updated, checked and removed.
- A cloud build with `agy` whose limits are real (enforced by Relevo's guard where the tool has none) and whose gaps are stated.

**Non-Goals:**
- Gemini CLI, Claude file generation, a change to the plugin.
- Proving that QA is as good with a Gemini model.
- Antigravity's browser, artifacts and review panels; the skills keep using `gh`, `git` and scripts.

## Decisions

- **The source stays in Claude Code's format; a renderer is a one-way transform** `{ id, scopes, render(source, ctx) → [{ path, content }] }`, pure, with writing done by `init`. Alternative: a neutral source plus two renderers (Claude included); rejected for now because it changes what Claude users get before anything is learned. A later renderer is one new file.
- **Skill names are `relevo-<name>`.** An Antigravity skill name allows lowercase letters and hyphens, so the colon cannot be kept, and a bare `go` or `status` would collide with other skills. The renderer rewrites `/relevo:go` to `/relevo-go` and `relevo:dev` to `relevo-dev` everywhere in the text, and a test fails if a `relevo:` token remains.
- **Skills only a person may start cannot be reserved in Antigravity.** Claude has `disable-model-invocation`; Antigravity documents nothing equal. For the skills that push or spend (`go`, `fix`, `ship`, `issue`, `review`, `init`, `think`) the renderer writes a description that says it runs only when the person types `/relevo-<name>`, and a first line in the body that makes the agent stop and ask when it was not started that way. This is a request to the model, not a control, and the security page says so. The guarantees that hold regardless are the scripts' gates: `go` refuses an issue that is not `ready`, with an unchanged hash, and `ship` needs a written confirmation. The first task checks whether Antigravity honours an extra frontmatter key for this; if it does, the renderer uses it.
- **Scripts are called through `relevo run <name>`**, which resolves the script in the installed package and prints the version it used. The renderer turns `node ${CLAUDE_PLUGIN_ROOT}/scripts/x.mjs` into `relevo run x`. Alternatives: copying scripts into the repository (many files, a second copy to protect) or `npx` per call (slow, network at run time). On the runner the workflow installs the pinned package once.
- **Subagents get an explicit tool list and a stated execution policy.** `relevo-qa` lists read, search and command tools and no write tool (mirroring `disallowedTools: Write, Edit`); the command tool can still write, as Bash does for Claude, and `go`'s diff check is the real control. `relevo-dev` lists read, write, edit, search and command tools. `commandExecutionPolicy` is chosen in the first task: `sandbox` (default) may block the stack's test commands; `auto` may be needed for `dev` and `qa`. The renderer maps tool names through a table and fails on a name the installed `agy` does not list, because a wrong name can hang a subagent. The table is filled from the installed tool, not guessed (*the names are unverified*).
- **Orchestration stays in the main session.** `go`, `fix` and `review` call `relevo-dev` and `relevo-qa` through `invoke_subagent`. That the call blocks until the report arrives, which `go` relies on ("wait for each report"), is *unverified* and checked first; if it does not block, the rendered text for `go` tells the agent to wait for each subagent's final message before it continues, and the guard refuses a run that ends with the issue still `building`, as the Claude template already does.
- **Where files go.** Project scope: `.agents/skills/relevo-*/` and `.agents/agents/relevo-*.md`. Machine scope: `~/.gemini/config/skills/`, `~/.gemini/config/agents/` and, for the CLI, `~/.gemini/antigravity-cli/skills/`; whether the CLI also reads `config/` is *unverified*, and until it is known machine scope writes both and lists both in the manifest. The cloud runner uses machine scope, so nothing is added to the working tree (the preflight requires a clean one).
- **A manifest** `.relevo/adapters.json` (machine scope: `~/.gemini/relevo-adapters.json`) lists tool, scope, package version and the hash of each file. `update` rewrites only files whose hash matches, reports the hand-edited ones (overwriting only with `--force`) and deletes files the new version does not generate. `.relevo/` is already protected.
- **The run guard is Relevo's, not the vendor's.** `agent-guard.mjs` starts `agy -p --output-format stream-json …` as a child in its own process group, counts turns and tokens as the events arrive, enforces `limits.run_max_turns`, `limits.run_max_tokens` and a wall-time limit (and always passes `--print-timeout`, because of the hang above), kills the group when one is reached and exits with a code the workflow maps to the same "ended without an outcome" comment the Claude template posts. It also fails the run when stderr reports a refused tool, because the vendor exits 0 on a soft denial. It is plain Node with the child injected, so it is tested with a fake process. That the stream carries turn and token counts as it goes, and not only at the end, is *unverified*; if it does not, turns and time are enforced from events and tokens only after the run, and the page says so.
- **Cost.** There is no cost limit in `agy`. `limits.run_max_cost` is rejected by `validate-config` when `agent.build` is `antigravity`, with a message that says why, and `limits.run_max_tokens` replaces it. The real ceiling is the quota and budget of the Google Cloud project the key belongs to; the docs recommend a dedicated key and project for Relevo, and say that a budget alert is not a cap.
- **Cloud controls** (the workflow writes them to `~/.gemini/antigravity-cli/settings.json` on the runner, outside the repository): `modelProvider: gemini`; `permissions.deny` for `read_url`, `execute_url`, `command(curl)` and `command(wget)`; `permissions.allow` closed to the file actions inside the workspace plus `command(relevo)`, `command(git)`, `command(gh)`, `command(node)`, `command(openspec)` and the stack's tools from its profile; `toolPermission` and `--sandbox` as the first task finds they behave; `GEMINI_API_KEY` from the secret store. The guard and the job's `timeout-minutes` bound time. A prefix allow list is not an operating-system boundary, as for Claude, and the page keeps saying it.
- **One workflow template, with the model step in a marked block.** `templates/workflows/relevo-go.yml` keeps the whole workflow and marks the model step with `# relevo:agent-step begin` and `# relevo:agent-step end`. The step, its credential, its limits and its usage report are exactly the non-neutral part. For `agent.build: antigravity` the generator that already writes the workflow (`relevo init` and the skill `init`) replaces only that block with the one in `templates/agents/antigravity-step.yml`; nothing else differs, so a change to the gates, the queue or the reports is made once. Alternatives: two full templates kept equal by a test (rejected: every edit twice), or a templating language (rejected: a block replacement is all that is needed). The usage report reads the guard's own summary instead of the vendor's log.
- **`relevo init` and `/relevo-init` are different things**: files for a tool versus the repository's labels and rules. The command was asked for by this name, so it keeps it, tells the person at the end that the other step exists, and `docs/install.md` has one paragraph on it.

## Risks / Trade-offs

- [`GEMINI_API_KEY` is in the environment of the agent's own commands, so the agent can read it] → a dedicated key restricted to the Gemini API, in a project with a quota; never a general Google key; stated on the security page. ADC is the stronger option and is documented only for a person at a terminal (*unverified* for a runner).
- [`agy -p` hangs without a terminal, versions 1.2.x] → outer timeout, pinned version, and a task that runs the real command on a runner first.
- [A soft denial exits 0, so a blocked tool looks like success] → the guard reads stderr and fails the run.
- [Reserved skills cannot be reserved] → description and first line, plus the gates in the scripts; stated as not enforced.
- [No turn limit in the tool and unverified event stream] → the guard; if the stream has no live counts the page says what is not enforced.
- [Generated files in the repository can be edited by the agent and steer later runs] → protected paths, the manifest hash, a doctor check, and on the runner a machine-scope copy generated from the pinned package.
- [Tool names, execution policy, subagent blocking, `config/` versus `antigravity-cli/` unverified] → first task group, with a stop rule.
- [Quality of adversarial QA with a Gemini model is unknown] → not claimed; a trial is recorded in `docs/pilot-findings.md`.
- [The marked block in the shared template is edited by mistake or its markers removed] → a test that the markers exist exactly once, and that the rendered Antigravity workflow differs from the Claude one only inside the block.
- [If the cloud run fails the verification] → the local adapter ships on its own (task groups 2 to 4 and 6 do not depend on group 5), and the cloud step falls back to Gemini CLI's action in a later change.

## Migration Plan

Nothing changes for existing installations: `agent.build` defaults to `claude`, the commands are additive, and the plugin is untouched. The changelog gets an Unreleased entry; the version is raised only when the maintainer prepares a release.
