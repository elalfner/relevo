# Changelog

All notable changes to Relevo are recorded here. The format follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/), and versions follow [Semantic Versioning](https://semver.org/).

## [Unreleased]

### Added

- **The commit of a run stopped at a limit names the tasks it holds (#167).** Only the checkpoints carried the `Relevo-Tasks:` trailer, so in the real runs of the sandbox the work kept at a limit (a replica and the fixes of QA) could not be found by task, and a template left in it could not be found by section. `wip: stopped by limit (#N)` now names, in that trailer, the tasks that are checked in the `tasks.md` of the change and that no commit of the branch over the base names yet (read by the rescue from the working tree, with a new `doneTaskIds`); with none, or when the file cannot be read, it is made as before. `replica-plan.mjs template --section K` also finds such a commit. The checkpoints, the QA-rejection commit, the count of checkpoints and the resume check do not change; a branch with limit commits made before this has no trailer and is found as before.
- **The usage comment says why each replica ran on its model (#167).** `replica-plan.mjs model` printed the reason (`one name below sonnet in agents.ladder, not below the floor haiku`, `the developer is not on auto, so the repository decided its model`, `this target failed 2 times on the cheaper model, so the stronger model builds it`) and nobody kept it. With `--task <id>`, which the `go` skill now passes, it appends the model and the reason to `replica-models.json` of the progress folder, as `model-plan.mjs` does for the plan, and `run-usage.mjs` shows after each replica `, because <reason>` (`, porque <reason>` in Spanish; the reason is quoted as written, like the reasons of the plan) and puts `why` in each entry of `replicas` of the marker. For a target launched more than once it is the reason of the last launch. A run with no record, or an older `go` skill, gets the comment it got before; the digest ignores the new key.
- **A resumed replicated build finds its template, and the usage comment shows the replicas apart (#167).** Two follow-ups of guided replication. A checkpoint (`wip: checkpoint k/n`) now also names the tasks of its group in a `Relevo-Tasks:` trailer (`checkpoint.mjs --tasks`), and `replica-plan.mjs template --section K` finds the template by those tasks instead of by the number of the group: a resumed run lists only the pending groups and numbers them again, so with the old lookup the template checkpoint of a build cut after two of four groups was not found (shown first with a failing test). A checkpoint made before this change names no tasks and is not found, as before: `go` then has the developer read `git log`. `go` launches each replica, and its fix, with the description `replica <task id>`; when replicas ran, the usage comment lists them apart from the other agents (per target: model, attempts, turns and an estimated cost, and the cost of the replicas against the rest of the run, written only when every figure is in the log) and the marker carries them under `replicas`. A run with no replica gets no such phrase or key. The texts are in the catalog in English and Spanish. The replica checkpoint, protected paths, the credential scan and the budget guard are unchanged.
- **A run stopped by a usage limit goes back to the queue by itself, and the quota is visible (#118).** The final step of the go workflow no longer marks the issue `qa-failed` for a usage limit: it returns it to `queued` and posts one comment that says when it will retry, with a hidden marker that holds the time and the number of the retry. The time is the reset time that the rate-limit event of the log gives (plus a minute, only when it is in the future and at most 8 days away); when the log has none, the retry is after a back-off of 30 minutes, then 2 hours, then 5 hours, and the comment says it is a back-off and not a prediction. The planner holds the issue until then (the queue and the decision of `go` both apply it; `relevo:ready` applied by a person overrides it), starts only one retrying issue at a time, and stops after 3 retries that again end at a limit: the issue is then `qa-failed` and the comment asks a person. The retry never discards work: it happens only when the rescue step kept the work (the next run resumes from it) or there was none, and when the comments cannot be read it stops instead of retrying. When the queue starts several builds at once it waits 60 seconds between dispatches. The usage comment adds, for each quota window of the log (`five_hour`, `seven_day`), the utilisation at the start and at the end of the run and the reset time when the log gives it, and the marker carries it under `quota`; a log without those events (an API-key repository) gets no quota line. New scripts `scripts/limit-retry.mjs` and `scripts/lib/limit-retry.mjs`; `usage-limit.mjs` prints the reset time. All texts are in the catalog in English and Spanish. An installed go or queue workflow keeps the old behaviour until it is updated. The quota fields were checked against the log of a real run (a subscription token: `rateLimitType`, `utilization`, `resetsAt` in seconds and `unifiedWindows` with the 5-hour and the weekly window); a rate-limit event of a limit that was really reached (`rejected`) has not been seen, so the reset time of a blocked window is read by the same fields and is used only when it is credible.
- **Guided replication: build one target, replicate the rest with a cheaper model (#135).** An issue can declare `Pattern: #N` (parsed like `Depends-on:`); `scripts/pattern-check.mjs` finds the pull request that closed #N into the base branch and writes its diff outside the working tree as the template, and `build-preflight.mjs --stage issue` reports a pattern that does not exist or is not merged (reason `inputs`; a lookup that fails is listed as unverified and never blocks). The recipe is declared in `tasks.md` (a `## Replication recipe` section with the template, and tasks marked `[replica]` with `Rename:` and `Differences:`) and checked by `scripts/replica-plan.mjs check` with no model; a replica with no differences sends the issue back with the reason `missing`. `task-groups.mjs` makes every replica its own group. `go` builds the template first and runs the gate and the QA lenses on it before any replica starts, launches one developer per replica in the new replica mode on the model of `replica-plan.mjs model` (one name below the planned model in `agents.ladder`, never below `agents.dev.floor`; the planned model once the same target failed the gate twice; `model-plan.mjs escalate` after that, or after two failures when the planned model is already the cheapest), runs the gate after each replica and the lenses once at the end. Replicas go through the same checkpoints, protected paths, credential scan, budget guard and `run_max_cost`; no configuration key was added. Not covered yet: a QA rejection is not attributed to one target, the rename is not applied by a script, a pattern of another repository is not read, and the lookup of the merged change has not been run against the live API.
- **A queued issue says its position, and every comment of the bot follows `language` (#127).** The comment for an issue that waits for a free agent lists how many runs are active and which issues they are, how many issues are ahead of it, and the median duration of the last ten builds of the go workflow (looked for among its last 30 runs, since runs that only decide have none) with how many there were; a figure that cannot be read is written `unknown` (`desconocido`) and nothing is estimated. The capacity comment lists the built issues that are waiting for review. The comments that the go workflow carried inline (the run failed before it decided, ended without a result, stopped at a usage limit, was cut and kept its work) now come from the message catalog (`run_failed_early`, `run_no_outcome`), and the usage sentence takes its phrases from the same catalog, so `language: es` is honoured everywhere; a run so early that the scripts could not be installed still posts one English sentence. A language that lacks a key renders in English, and `tests/messages-language.test.mjs` fails the build of Relevo when a language lacks a kind or a phrase of English or changes a placeholder. The `decide` job has `actions: read` for the durations (read only); without it the duration is `unknown`.
- **`doctor` reports a workflow that uses an action that runs on Node.js 20 (#132).** `automation.action-pins` names the file, the line and the action for `actions/checkout`, `actions/setup-node` and `actions/create-github-app-token` up to the Node.js 20 releases and for `supabase/setup-cli` v1 and v2; a commit pin is judged by the version in its comment. It never changes a file, and a pin chosen on purpose is reported but kept.
- **Long test runs go through one script, the gate does not repeat a green check, and the comment shows the seconds per check (#124).** `scripts/long-run.mjs` runs a command that takes minutes in the background with a log and a one-line status (`start`, `status`, `wait`, which returns before the 2-minute limit of the agent's shell tool); the log stays readable if the job is killed. `go` runs the gate through it, and the developer runs the full suite as `--check test`, whose command comes from the profile. A check that passed on the same diff, command and folder is not run again by the gate and the receipt marks it `reused`; a key that ever failed is always run, so reuse never hides a red result, and no option records a result without running it. Every lens reads the receipt and runs no tests. The run comment lists the seconds of each check, and its marker carries them under `checks`.
- **`/relevo:issue` warns about protected paths and unconfirmed names, and the hand-off lists assumptions and shared code (#119, #122).** `check-issue.mjs` warns (never fails) when the text asks to change, or for a hard path only names, a path that an unattended run does not change (the rules file, a workflow, `relevo.yml`, a skill folder, a dependency manifest that no `Allow-paths:` covers), offering the two ways out; and when an assumption names a permission, endpoint or field that no file of the repository holds, offering to confirm it, keep it as a `manual` input or ask it as an open question. `build-preflight.mjs --stage spec` lists the same kind of assumption from `design.md` (`assumptions`, `assumed`) without stopping the build, and `scripts/shared-code.mjs` lists the changed files that more than one file imports or that live in a shared folder; `go` puts both in the hand-off ("Assumed, not confirmed", "Shared code touched"). A run that the commit guard stopped for a protected path no longer says "QA still rejected it after the retries": the comment names the policy and its next step is `/relevo:issue`; the `policy` hint no longer talks only about dependency manifests.
- **An issue that contradicts the project rules is caught before the build, and a violation of a hard rule blocks (#121).** `check-issue.mjs` and the build preflight compare `Out of scope` with the rules of `qa.rules_from` and with the issue's own scenarios, with no model, and quote both lines; a conflict sends the issue to `needs-spec` with the new reason `conflict`. A decision can override a rule with `Overrides: <file>:<line>`; a rule marked `[advice]` never blocks. A QA finding that cites `Rule: <file>:<line> "<quote>"` of a hard rule blocks when `qa-aggregate.mjs` finds the quote on that line, even from the `interface` lens on the last attempt or in a `QA PASSED` report.
- **The `context` of `openspec/config.yaml` reaches the developer, which has a short cost guide by default (#130).** `go` gives `relevo:dev` the `context`, the `rules` for `tasks` and the apply guidance, word for word; `agents/dev.md` carries a four-line cost guide (bounded reads, scripts for repetitive files, only the tests of what changed, never rerun the gate) that project rules override.
- **`scripts/gate-selftest.mjs` checks the gate without throwaway pull requests.** It seeds a failing unit test, a failing browser story and a docs-only change in a detached scratch worktree, runs the validation gate on each and reports what it did against what the case expects. It never writes to the base branch or the working tree, leaves no branch, skips a case the stack cannot seed and says why, and prints the cases as instructions when the CI is not Relevo's. The steps for the remote CI aggregate are printed, not run.
- **The QA lenses run together, and the agent is given the path of the scripts it runs (#125).** `go` launches the active lenses in one turn once the receipt is valid and waits for all the reports; the receipt is still checked right before each launch, a lens that gives no report is asked once more and then named in the failure, and `lens-plan.mjs --max-parallel <n>` prints batches for a runtime that limits concurrent subagents. `progress.mjs lens` has `--end`, so the seconds of each lens are right when lenses overlap. The `spec` lens is given the resolved path of `issue-sections.mjs` instead of searching the filesystem for it.
- **`doctor` and `init` report the environment findings of the pilot.** `doctor` names a linked repository it cannot read and what to grant, prints both runners when a repository variable overrides `runner.labels`, warns when the pinned `RELEVO_VERSION` is older than the published one (naming what changed; skipped with a note offline), and warns when the base branch requires no status checks. `init` lists each as a step for the person and changes no token, variable or branch rule. `doctor` stays read-only.
- **A retry of the developer runs one level up (#134, second stage).** After a red gate or a rejection by QA, a developer on `auto` is relaunched one name up `agents.ladder` and never past its `ceiling` (`model-plan.mjs escalate`); a model written in `relevo.yml` stays, and the lenses are not raised. With the default ceiling a retry never costs more than the defaults. The usage comment and marker (`escalated`) say each step. A retry for `tasks left unfinished` does not exist yet, so it is not covered.
- **A QA lens on `auto` is never below `sonnet` by default (#134).** The lens evaluation with cheaper models passed `sonnet` for `spec` and `security` (7/7, no false positive) but not `haiku` for `code` and `interface` (it flagged 2 of 4 clean changes). A `floor` written in `relevo.yml` is still obeyed. The evaluation takes `--model <name>` to run every lens with one model.
- **A reviewed false positive of the credential scan can be let through, with a reason (#120).** `.relevo/scan-exceptions.json` lists entries with a `path`, a `pattern` and a `reason`; a credential finding on a file that matches the path, on a line that contains the pattern, is no longer reported by the safe commit or the validation gate, wherever the line moves to. Every other finding is refused as before and temporary markers are never excused. Entries that are too broad (a folder, `**`, a bare `*`, a pattern under 8 characters, no reason) are refused and named. The list is read from the last commit, not from the working tree, and `.relevo/` stays a protected path, so an unattended run cannot edit it. The number of exceptions applied, with path and reason, goes to stderr of `commit-change.mjs`, to the receipt of the gate and to the run comment.

### Changed

- **The docs say that a replica is cheaper only when the developer is on `auto` (#167).** Found in real runs of the sandbox: the default `agents.dev.model` is written (`sonnet`), so `replica-plan.mjs model` answers that the repository decided and every replica runs on `sonnet`; with `agents.dev.model: auto` a medium change plans the developer on `sonnet` and its replicas ran on `haiku`, while a small change plans `haiku` already and a replica has nothing cheaper. `docs/execution.md`, `docs/configuration.md` and `docs/issue-format.md` (and their Spanish versions) now say so, with the setting to use. Documentation only: no script, workflow or default changed.
- **The workflow templates pin current actions by commit, and the build caches its downloads by version (#132).** `actions/checkout` v7.0.1, `actions/setup-node` v7.1.0, `actions/create-github-app-token` v3.3.0 and `supabase/setup-cli` v3.2.0 replace the Node.js 20 releases that printed a deprecation warning on every run, each as a full commit with its version in a comment and verified against the repository of the action; `claude-code-action` is unchanged. `create-github-app-token` v3 marks `app-id` as deprecated in favour of `client-id` (another value), so repositories that use the App keep a notice about the input. The build job installs Bun at `BUN_VERSION` (1.4.4, the one `claude-code-action` installs and downloads again on every run) and gives it to the action through `path_to_bun_executable`, and caches Bun and OpenSpec under a key with the pinned version, the system and the architecture. A restored Bun must report `BUN_VERSION` or the job stops before the agent. Every cache is saved right after the install and before the agent starts, never when the job ends, and every `setup-node` step sets `package-manager-cache: false`, so nothing the agent does can reach a cache that a later run restores. `tests/workflow-pins.test.mjs` fails on a tag, a wrong commit, a cache saved after the agent or a missing version in a key.
- **`ship` retries a mergeability that GitHub has not computed, and says which checks it relied on.** When GitHub answers that it has not finished checking whether the pull request can be merged (usual right after the archive push), the ship by label waits and looks again for about 90 seconds, keeping the label; if the state never settles it stops, removes the label and says so. The comment after a merge names the commit whose checks it relied on (the merged commit, or the approved head when the archive commit had none) and what the checks of the merged commit were when it was merged. `/relevo:ship` gets the same retry and report. Issue #126.

### Fixed

- **A run that stops for a reason other than QA no longer says that QA rejected it (#181).** Found in a real run of the sandbox: an issue whose text changed after a cancelled run stopped at `branch already exists`, and the comment said `failed QA ❌` and "QA still rejected it after the retries". The title and the line that says what happened now say that QA rejected the work only for a QA rejection (`QA rejected after the retries`, `QA rejected: nothing the developer agent can fix`, or no reason). Any other reason, including one the catalog does not know, is reported as a stop (`stopped ❌` / `se detuvo ❌`, "QA did not reject the work"). `/relevo:fix` finds the comment by its title, so `failure-comment.mjs` accepts the new titles as well as the old ones. The next step and the text of the usage-limit and protected-path stops are unchanged.
- **The comment of a cut run names how many checkpoints the branch holds (#167).** The comment of #172 had a wording for a known number of checkpoints, but the go workflow never sent it, so every real comment used the generic one. `rescue-work.mjs` now counts the checkpoints over the base branch with the rule of the resume check and writes `checkpoints=` (only when it could count: an unknown is never `0`, which would say that none was saved), and the report step passes it to the comment. Two lines of `relevo-go.yml`; no text of the catalog changed.
- **Two comments of the bot say what really happens (#167).** Found in the real runs of the sandbox. The comment for work kept after a cut run no longer says that `relevo:ready` builds "from the start": on the branch of the issue it resumes from the last checkpoint (or from the work kept) and builds only the pending tasks, and says that a changed issue text or a commit by a person stops it instead (`checkpoints` is optional; the workflow does not send it yet). The queue comment says "Running or starting now", because the count includes the issues the same evaluation is about to start. No guard changed.
- **An issue that a usage limit returns to the queue keeps the `queued` label (#167).** Found in a real run of the sandbox: the final step of the go workflow removed `relevo:queued` and added it in one `gh issue edit`, GitHub applies the removal last, so the issue ended with no state label, the comment said it was back in the queue and no queue pass could find it. The retry command no longer removes `queued`; the tests of the final step now run against a `gh` that applies label edits as GitHub does, with scenarios for an issue that was building, ready or already queued and for renamed labels, and a test over the templates that no `gh issue edit` adds and removes the same label. An installed go workflow keeps the defect until it is updated to this template.
- **Three guards that failed open now fail closed (#161, #162, #163).** Found by a code review of #160; each was shown by a test that failed before the fix.
  - **A real problem no longer becomes a note by citing an advice line (#161).** In the `spec`, `security` and `code` lenses (the ones that always block), a finding that cites a rule marked `[advice]` is an advisory note only when its own text repeats the words of that line; a vulnerability that carries an advice line on the side blocks. A hard rule still decides first, an unverified citation is unchanged, and the `interface` lens is unchanged. A finding that merely paraphrases an advice rule on those lenses now blocks, so quote the rule in the text or give the advice as a note with no `Rule:` line, as the lens instructions already say.
  - **An issue cannot put a role below its `floor` (#162). Breaking for whoever relied on it:** `Model:` and `QA-model:` were clamped to the `ceiling` only, so `QA-model: haiku` ran every lens on `haiku` under a floor of `sonnet`. A value below the floor is now raised to it and the plan says so, each lens by its own range. The default model that a role gets when there is nothing to score is kept inside the range too (a floor above it raises it, a ceiling below it lowers it, a name the ladder does not have is replaced by the floor). A repository that wants a cheaper model lowers its own `floor`. The plan that `go` falls back to when the plan cannot be made is not changed.
  - **A scan exception excuses the finding it describes, not the line (#163).** The `pattern` of an entry of `.relevo/scan-exceptions.json` has to sit on the text that the credential matched (hold it or lie inside it); a second credential on the same line, a second key of the same kind, or a pattern that only appears next to the credential is reported and the line is not excused. A line that moves is still excused, and an entry whose pattern sat beside the credential instead of on it now reports the finding until a person edits it.

## [0.14.5] - 2026-11-05

### Added

- **A run stops launching agents after a limit.** The runner counts only the turns of the main agent, so the subagents (the developer and the QA lenses) were never stopped: a pilot build used 144 turns against a limit of 100, 113 of them by subagents. `go` now records each agent when it finishes, copying the three numbers of the `<usage>` block that ends its report, and asks the new `scripts/run-budget.mjs check` before it launches the next one (the developer again, or the next lens). When the turns of the subagents together reach `limits.run_max_turns`, or the run has lasted `limits.run_max_minutes`, no other agent starts and the run takes the failure path with the reason `run limit reached`, naming the agents that did not run. The guard fails open: it stops a run only on a figure it can read.
- **`limits.run_max_minutes`** (default 50, at least 5), the soft time limit of a run. The decision that starts a run carries it, and `/relevo:doctor` warns when the `timeout-minutes` of the build job of the installed go workflow is not at least five minutes above it.
- **The work of a run that stops at a limit or is cut is kept.** Before, the failure path (run by the agent) kept the work only after a QA rejection; a run cut by the runner or by the 60-minute job timeout left nothing. `go` now commits the work as `wip: stopped by limit (#N)` when it stops at a limit, and the go workflow has a step that always runs, **Keep the work of a run that was cut**, which does the same for the working tree that is left when the issue is still `building` or `ready`. Both go through `commit-change` (protected paths, restricted files, temporary markers and credentials), push to the branch of the issue without force, and overwrite nothing: they push only a fast-forward of what the remote has, and leave alone a remote branch with commits that the run does not have. The comment of the run says whether the work was kept, and `/relevo:fix` continues from it (`fix` recognises both `wip` subjects).
- **The comment about a cloud run lists each agent and each model.** For the main agent and every subagent: model, effort, turns, minutes and an estimated cost; and the real cost of each model, from `modelUsage`. The cost of an agent is a share of the real cost of its model by the weighted input side of its messages, written as "about"; the estimates of a model add up to its real cost. The hidden marker carries the same figures under `agents` and `models`; the digest ignores them. Checked on the log of a real build: the developer came out at about 49 % of the cost and the specification lens at about $1.0, which agrees with what a person measured by hand.
- **The outcome class `limit`** in the usage record and in the digest, for a run that stopped at a limit or was cut.
- **The comment of a run cut by the runner says which limit it was.** The new `scripts/run-cut.mjs` reads the result of the execution log (`error_max_turns` or `error_max_budget_usd`), and the report step says "the runner stopped it at its turn limit (--max-turns)" or "at its cost limit (--max-budget-usd)". A job that was cancelled or timed out has no such result and keeps the general wording.
- **The budget guard says what it could not use.** `run-budget.mjs check` adds `notes` to its line: an option that is not a whole number (`--max-minutes 7.5`) and a `relevo.yml` that does not validate, whose limits are then not read. It still fails open, but it no longer switches the limits off in silence, and `go` mentions the notes in its report.
- **`go` builds every group with the developer and makes the checkpoint of every group.** In a real run the agent did the documentation group and the checks itself and called the checkpoint with `--k 1`, `2` and `4` of 4: the files of group 3 went into the commit of group 4. The skill now says that every group goes to the developer, that two groups are never run in one launch, and that every checkpoint is made in order with its own number, even when no file changed. It depends on the agent following the instruction.
- **A run that ended by itself with no result is class `other`, not `limit`.** The rescue step of the go workflow set `limit` on every run that ended with no outcome. The first real run in the sandbox ended after 2 turns because of the preflight, and its usage record said `limit`. The step now sets `limit` only when the runner cut the agent (turn or cost limit, read from the log with `run-cut.mjs`) or the agent step did not succeed (failed, cancelled or timed out), and `other` otherwise.
- **The QA lenses leave out what the install step left.** The run that followed showed the spec lens rejecting the work for `analysis_options.yaml` and `pubspec.lock`, which `flutter pub get` had rewritten and the developer never touched. `scripts/tree-baseline.mjs list` prints the files that are still as the install step left them; the QA reference gives that list to every lens as `not_the_change` once per round, and the four lenses leave those files out of the diff they read and report no finding about them. A file the developer changed afterwards is not in the list.
- **The clean-tree check of the preflight ignores what the install step left.** The first real run with the baseline showed the next problem: on a current Flutter, `flutter pub get` also rewrites `analysis_options.yaml`, and the `clean-tree` check of `scripts/preflight.mjs` that `go` runs first refused the working tree, so the agent stopped after 2 turns with nothing built. The preflight now reads the baseline recorded before the agent and does not count a file that still has that content; a file changed afterwards still stops the run, and a local run, which has no baseline, counts every change.
- **The rescue and the checkpoints no longer take the install step for the work of the agent.** A real run in a Flutter project showed that `flutter pub get` rewrites `pubspec.lock` before the agent starts; the safe commit refuses a dependency file the issue did not list, and refuses the whole commit with it, so the work of the agent would be lost with the lockfile. A new step of the go workflow (`scripts/tree-baseline.mjs record`) records, before the agent starts, a fingerprint of every file that already differs from the commit. The rescue and the checkpoints leave out a file that still has that content, and judge a file the agent changed again like any change. A restricted file is never opened for this and is never left out; without a baseline everything stays in.
- **The rescue keeps edits made outside the branch of the issue.** When the run never left the base branch (or a detached head), the edits are carried to a new branch of the issue and kept there, so nothing is lost with the runner; the base branch is never committed to. On any other branch, or when the branch of the issue already exists, the edits go to a separate `rescue/<branch>` branch from where the run stands, and the comment says it is not the branch `/relevo:fix` reads. Nothing is pushed to the base branch.
- **The developer builds one section of tasks at a time, with a checkpoint after each.** `go` splits the pending tasks with the new `scripts/task-groups.mjs` (one group per section of `tasks.md`; three tasks or fewer are one group), launches the developer once per group, and after each group `scripts/checkpoint.mjs` commits the files that changed as `wip: checkpoint <k>/<n> (#N)` and pushes the branch of the issue. The commit carries the hash of the issue text as a trailer and goes through the same safe commit as every commit. A cut or a limit now loses at most the group in progress, and each launch starts with a shorter context.
- **A later run resumes from the checkpoints.** Before, an existing remote branch always stopped the run with `branch already exists`. Now `scripts/resume-check.mjs` resumes when every commit over the base is one that Relevo made for the issue (the specification, a checkpoint, or the work kept at a limit), the tip is a checkpoint or a limit commit with the hash of the issue text, and the text has not changed: the run continues from the branch, writes no specification and builds only the pending tasks. A commit of a person, a changed text, work that QA rejected, or a branch with only the specification still stops with `branch already exists`.
- **`commit-change.mjs --allow-empty`** makes the `feat:` commit with no change when the checkpoints already hold the files and nothing else is staged, so that the branch still ends on the commit that `review` and `ship` expect.

### Changed

- **The rescue and the failure path overwrite nothing instead of refusing every existing branch.** The branch of the issue is on the remote after the first checkpoint, so "never touch a branch that already exists" became "never overwrite": a push is made when the remote tip is an ancestor of the working branch (a fast-forward), and a remote branch with commits that this run does not have is left alone. The commit of a run stopped at a limit carries the hash of the issue text, which makes it resumable.
- **The text of the failure comment for `run limit reached`** says that the run stopped at a limit before it finished and that the branch holds the work done before the stop; it no longer says that QA rejected it. The first line stays the same, because `fix` finds the comment by it.
- **The `go` skill no longer says "do not try to stop early".** It says that the counters of the runner cannot be seen and that the only limits it checks itself are those of the subagents and of the time, with the guard.
- **`model: auto` and the model for each issue** (#134, first stage). A role of `agents` (`dev` or a QA lens) can be `auto`: a script, `scripts/model-plan.mjs`, picks its model once before the first launch, between a `floor` and a `ceiling`, and `go`, `fix` and `review` launch every agent with the plan. `agents.ladder` (default `[haiku, sonnet, opus]`) gives the order of the models; the default range of a role is its default model and one step below, so `auto` costs no more than the defaults unless a ceiling is raised, and the security lens is never below `sonnet` by default. The pick is placed by the size of the change (pending tasks plus scenarios: up to 6 the floor, up to 14 the middle, more the ceiling) and raised one step by a dependency file in `Allow-paths:` or a security-sensitive area; the security lens goes to its ceiling in both cases. An issue can carry `Model:` (developer) or `QA-model:` (every lens): it is read only for a role on `auto`, lowers freely, is clamped to the ceiling, and is ignored with `trust: public` or for a name outside the ladder. `/relevo:issue` may propose the line with its reason. The usage comment and its marker say which model and effort each role used, where the choice came from and why (`plan`), and a run without a plan gives the comment it always gave. The plan fails open: if it cannot be made, `go` uses the configuration and says so.
- **`/relevo:init` and the templates** carry `limits.run_max_minutes`; the workflow templates move to 0.14.5, so `/relevo:init` reports older copies.

### Known limits

- The checkpoints and the resume have been tested with temporary git repositories and a bare remote, not in a real cloud run: that the push of a checkpoint works with the credentials left by `actions/checkout` after `claude-code-action` has run has not been seen, and a checkpoint that cannot be pushed is reported but does not stop the build.
- A checkpoint pushes unreviewed work to the branch of the issue while the issue is still `building`; no pull request is opened. The checkpoints stay in the history of the branch (squashing them needs a force push) until `ship` squashes the pull request.
- Only the sections of `tasks.md` are checkpoints, not each task; a section with many tasks is lost whole when a run is cut inside it.
- A resumed run does not add the cost and the minutes of the earlier run to its own limits or its comment.
- The result in a real cloud run has to be checked by a person. The `<usage>` block at the end of a subagent's report and the fields of the execution log were read in the log of a real build, but they are details of the runner, not a contract: when they change, the guard stops nothing and the comment leaves the agents out.
- The step that keeps the work pushes with the credentials that `actions/checkout` left in the repository. That the push works after `claude-code-action` has run has not been seen on a real runner; when it fails the comment says the work could not be pushed.
- The turn limit is two caps, not a sum: the runner limits the main agent and Relevo limits the subagents together. The main agent's turns are not counted inside the run, and an agent that is already running is not stopped in the middle, so one long agent can pass a limit by its own length.
- The cost per agent is an estimate. The output tokens are left out of the shares because the `usage` of a streamed message is a snapshot taken before the answer is complete.
- The model plan has not been run in a real cloud run. The thresholds of size (6 and 14) and the list of security-sensitive words are estimates to tune with the plans of the comments. The effort is not scored (it stays the configured one), the signals are those known before the build (no signal from the diff and no similarity with an earlier change), and there is no escalation on retry yet: a wrong pick of a smaller model is visible in the comment but not corrected during the run. That `go` launches every agent with the plan depends on the agent following the skill.
- A run cut by the 60-minute timeout still needs the job to live long enough for the step to run; `limits.run_max_minutes` leaves the last ten minutes for it, and `doctor` warns when it does not.

### Fixed

- **The ship by label no longer stops with "Resource not accessible by integration" when it reads the protection of the base branch.** To know whether the base branch requires checks, the run read the classic protection from `branches/<b>/protection`. That endpoint needs an administration permission that the workflow token can never have, so the run stopped on a private repository on the free plan (where 0.9.2 had only taught it to accept the plan refusal of a personal token) and on any repository whose rulesets answered normally. When the rulesets endpoint refuses because of the plan, the run now does not read the classic protection at all. Any other failure to read either still stops the run before anything is archived: checks that exist are never skipped because they could not be read. `/relevo:ship <n>` was not affected.
- **The last step of the ship workflow no longer fails on every run.** "Report a run that ended without an outcome" runs outside the checkout, so `gh` could not tell the repository and stopped with `not a git repository`. A ship that merged was then marked as a failed run, and a run that really ended without an outcome kept its label with nobody told. The step now names the repository with `GH_REPO`. Copy the change into your `.github/workflows/relevo-ship.yml` together with the new `RELEVO_VERSION`.

- **A design reference to a private linked repository no longer sends the issue back with a 404 when `RELEVO_LINKS_TOKEN` can read it.** The agent fetched the references itself, inside a job that never gets that token, so it read with the workflow token, which sees only the current repository. A step before the agent now fetches them with the token, which the agent still never holds. A file that cannot be read now says why: that `RELEVO_LINKS_TOKEN` cannot read that repository, that a private repository needs it, or that your `gh` login cannot read it, and the reason reaches the issue word for word. To adopt it, give `RELEVO_LINKS_TOKEN` read access to the contents of the linked repositories (Contents: read) and copy `.github/workflows/relevo-go.yml` again.

- **A false "usage limit" comment is no longer posted.** The runner writes rate-limit events all through a healthy run, with status `allowed`, and their name alone was read as a limit. A usage limit is now read in a structured log only from the text of a final result that is an error, or from a rate-limit event whose status is not `allowed`.
- **The count printed by `checklist` is plain text when the terminal forces color.**
- **`doctor` warns when the denials of restricted files in `relevo-go.yml` are stale or missing,** and `/relevo:init` refuses a merge that drops the `relevo:restricted` markers. A restricted file that the base branch versions is now reported as "versioned on the base branch" in the failure of `go`.
- **`.env.sample`, `.env.template` and `.env.dist` are example files and are not restricted,** like `.env.example`.

### Known limits

- Restricted files: the sandbox read denials and the `settings` input of the action were checked on macOS and in the source of the action, not on a Linux runner; the cloud workflow does not enable the sandbox until a full cloud run shows that the build still fetches, comments, labels and pushes with it on, so there a process that opens files itself is not covered and the cloud relies on the `Read` denials and on the tree. Antigravity denies by exact path only, its denial does not reach the shell, and a file created after the run starts is not covered. A command that reads without naming the file (`grep -r`) is not covered by a `Read` rule. A name outside the list (`key.json`) must be added to `restricted_paths`. The tool denials of Claude cover the common `.env.*` variants, not every one: `.env.docker`, `.env.backup`, `.env.old` or `.env.stage` is restricted for Relevo's scripts and the worktree but gets no tool denial until it is added to `restricted_paths`. A repository that versions `google-services.json` or `GoogleService-Info.plist` on purpose fails every run with "restricted file in the diff". The check is by name and a symbolic link to a restricted file is not followed.

- The Antigravity IDE route cannot be detected, so `doctor` says it exists and never says the skills are missing there.
- A cloud run with the default skills in the folder of a platform was not tried, and neither was whether a subagent discovers a skills folder nested in a platform by name; `dev` and `qa` read the skills through the paths Relevo gives them.

- `limits.concurrent_agents` counts the issues labelled `relevo:building` when the gate of an issue runs, and the gates of different issues do not wait for each other: with two or more runners, or on GitHub's runners, two issues labelled together can both start and exceed it by the number of gates that overlap. With a single runner the gates queue and the limit holds.
- The risks of runners sharing a home, caches, Docker and ports were not tried on a machine with several runners; the text says what can collide, not what was seen to.
- The skills of Boost for Livewire, Inertia, Flux, Tailwind and Pest are not listed by the `laravel` profile: each is up to 10 KB and applies only when the package is used. A project lists the ones it wants.
- The community Vue skills are unofficial and an early experiment by their author's own words. `vue-best-practices` tells the agent to read four reference files (about 34 KB) in every Vue task, so it adds about 44 KB of reading per run; it can be switched off with `skills.disable`.
- `boost:install --no-interaction` installs for the agents it finds on the machine, so on a machine with none that Boost detects it may install nothing; `doctor` then shows Boost present with no skill committed.

- Reading the summary with a real workflow token was checked on public repositories without a token, not yet in a workflow run on a branch whose classic protection requires checks. If GitHub left the summary empty for that token, the run would see no classic checks and GitHub would still refuse the merge of the archive commit, which the ship reports; nothing is merged around a protection.

## [0.2.0] - 2026-10-20

### Added

- **Where `go` builds** is derived, not configured: from the workflows that are installed, the model secret that exists and the new repository variable `RELEVO_CLOUD_GO` (`off` pauses the cloud at once, with no pull request; the queue pauses with it). A cloud without a credential no longer fails: the issue stays `ready` and a comment says to run `/relevo:go <n>` on a machine or to add the secret. See [Where `go` runs](docs/execution.md).
- **`go-local.mjs <issue>`** (and `/relevo:go <n> --local`) builds an issue on a person's machine, in a separate git worktree, with the same turn and cost limits and the same closed tool lists as the workflow (written once in `scripts/lib/run-flags.mjs` and compared with the template by a test).
- **Two credentials**: `doctor` deduces `api_key` or `subscription` from the secret name, warns when both exist, shows the state of the pause variable, reminds to read Anthropic's current terms for a subscription, and warns when a subscription is used with more than one concurrent agent. `init` asks where `go` runs and with which credential, switches the credential line of the workflow and sets `concurrent_agents` to 1 for a subscription.
- **After each cloud run** a comment gives the turns, the cost (notional with a subscription) and the tokens read from the agent's execution log, when it has them; a run that stopped at a usage limit or an empty credit says so and tells you to label the issue `ready` again later. The log format and the limit messages are not documented, so both readers are tolerant and say nothing when unsure.
- **`status`** lists the `ready` issues assigned to you with `/relevo:go <n>` when the cloud is not building, and alerts about an issue stuck on `building` (`limits.building_alert_hours`, default 3).
- **Dependencies between repositories**: `Depends-on: owner/repo#N` names an issue of another repository, and the new `links` setting of `relevo.yml` is the closed list of repositories an issue may depend on. The gate waits until the other issue is closed as completed, notices on the queue's schedule, and reads private repositories with a read-only token stored as the secret `RELEVO_LINKS_TOKEN` (public ones need none). An issue that names a repository outside `links`, or whose dependency cannot be read, says so instead of building.
- **`status`, `doctor` and `init` know the links**: `status` shows what a blocked issue waits for in another repository and its state; `doctor` checks that each linked repository can be read and that the secret exists (its name only); `init` asks for `links` and reminds about the secret.
- **`issue` drafts the other side**: when a feature depends on work in a linked repository it drafts that issue, shows it whole, creates it there only if asked, and offers to reuse the `## Data contract` of the issue it depends on.
- **`Platform:` line** in the issue: an issue names the one platform it is for (required with several platforms in `relevo.yml`, optional with one). `go` resolves it, passes the platform, stack and folder to the agents, and a draft without it fails the check. `fix` and `review` find the platform again with the new `platform-of.mjs`.
- **Scope of a commit**: `commit-change.mjs --within <folder> --change <id>` refuses files outside the folder of the platform (the change's specification, `GLOSSARY.md`, `docs/adr/` and `Allow-paths:` aside); the reason is "outside the platform".
- **`fix` keeps the work QA rejected**: it is saved in a stash named `relevo-fix #<n> iteration <k>` (`fix-stash.mjs`), the tree is left clean and the next `fix` offers it back. A branch that holds only the specification is recognised (`branch-work.mjs`), and the task list is checked before the developer and before the commit (`fix-tasks.mjs`): only the corrections are open, one of them a `Test:` task unless it is `(device only)`.
- **`ship` is safer and repeatable**: an approval counts only for the commit it was given on (or the head recorded at the start, across the archive commit), the issue must be `pr-open`, the change is validated and has no open task before archiving, and an already archived change skips the archive (`archive-state.mjs`). A conflict inside `openspec/` after the archive is recovered with a revert, a merge of the base and a new archive, with normal pushes (`conflict-scope.mjs`).
- **Who may run `ship`**: with `review.merger: approver` the person must be a member of `team.members`, not the author or the spec writer, and in `roles` mode one of `team.approvers`; an eligible person who did not approve confirms in writing that they did not.
- **Issue format v2**: optional sections for what the agreement settled (`Outcome`, `Decisions` with ids `D1`..., `Constraints` with `C1`..., `Code pointers`, `Verification`, `Assumptions`, `Open questions`) and a `Related:` line; earlier issues still pass. `go` copies those sections word for word into `design.md` ("From the issue: ...", through the new `issue-sections.mjs`), and `qa` rejects a build that breaks a decision or a constraint, citing its id. See [Writing an issue Relevo can build](docs/issue-format.md).
- **Open questions block the build**: a question under `Open questions` or the text `NEEDS CLARIFICATION` fails `check-issue` and sends a ready issue back as `ambiguous`, whose next step names `/relevo:think #<n>`. A body over about 8,000 characters passes with a warning.
- **Nothing is lost between `think` and `issue`**: `think` writes what it settled with ids before it asks for the reserved interview, and `issue` checks with `issue-coverage.mjs` that every id reached an issue or was discarded on purpose. `/relevo:think #42` starts from an issue that came back.
- **`issue`** asks, in a separate question after creating, whether to apply `ready` (and swaps `needs-spec` for `ready` after an update), searches for similar open issues first, reads only the specifications the issue touches, and keeps its update flow in `skills/issue/references/update.md`.
- **`review` starts with a brief** (`review-brief.mjs`): about five lines with fixed caps, computed from the issue and the `built` comment.
- **Not yet**: the `Design reference` section (pictures and example code for the front) comes in a later change, after the download of pasted attachments is tried against a private repository.
- **`review` audit without evidence is not a pass**: an empty device log, or one with no line from the app, now gives `REVIEW INCONCLUSIVE` (before, the empty log passed and a log without the app's process was audited as a whole). It cannot be waived, and `decide` refuses it.
- **Waivers**: the person can write `waive <number> <reason>` for a finding; with every finding waived the verdict is `REVIEW PASSED (with waivers)` and the pull request body lists them with the reasons. The agent never proposes one, and a fix that changes the specification clears them.
- **`review` is safer around the pull request**: a micro-fix is committed (with the scan) before the pull request opens, the remote branch is brought in before the base is merged, the assignee is compared with who runs it, an existing pull request is reused, and the log is kept with `review-state.mjs drain` as the person tests.
- **Review adapters and an Autopilot**: `review.autopilot` (`off` by default, `precheck`, `verify`) and `review.allowed_origins` in `relevo.yml`. `review` now asks `review-adapter.mjs` how a platform and target are reviewed (a device with `adb`, or a browser; iOS says it is not available yet) and stops before changing anything when there is none. With the autopilot on, the agent walks the checklist and records its own result per line (`precheck`), or marks lines it proved (`verify`), while the person confirms and agrees; the pull request lists what was verified automatically. A web target runs a Playwright script that `qa` reads first, in `web-review.mjs`: a clean browser that can reach only `localhost`, the page and the allowed origins, with credentials passed by variable name and redacted from the output. The audit understands a browser log. `doctor` checks `lib/main_driver.dart`, the `flutter_driver` dependency and Playwright. The default is `off` because the Flutter driver flow has not been run against a real app.
- **Profiles for Vue and Laravel** (`stacks/vue.md`, `stacks/laravel.md`), written and run on projects created for the purpose. The commands QA runs are read-only (the `lint` script of `npm create vue` uses `--fix`, so the profile calls `vue-tsc`, `eslint` and `vitest` directly through `npx --no-install`; Laravel uses `pint --test` and `php artisan test`), and each body says which defects the commands catch and which QA has to find by reading. A repository replaces a command (pnpm, `oxlint`, PHPStan) with `platforms.<name>.checks`. `doctor` knows how to install `composer` and `npm`.
- **Questions for the issue writer**: a profile can have a section `## Questions for the issue writer`, kept out of what `dev` and `qa` receive (`stack-profile.mjs --role issue` prints it) and asked by `/relevo:issue` when the idea leaves them open.
- **Documentation**: a [Guide](docs/guide.md) (the life of an issue with the command of each step, what to do when a review finds a failure, a reviewer asks for changes, QA fails, the quota runs out or the behaviour is unknown, fix or a new issue, cloud or local, credentials and limits, public repositories) and a [Security model](docs/security.md) that says what Relevo protects and what it does not, both in English and Spanish. The page on the issue format now has a Spanish version; the commands page gives the argument and an example of every command; the configuration page covers every setting, the profile layers, `checks` and what the limits mean with each credential. Tests check that every command, script, label and file a page names exists, that every setting appears on the configuration page, and that the guide says what the hand-off messages say.
- **Design reference**: an optional `## Design reference` section in the issue points to a file of the repository, a picture pasted into the issue, a file of a linked repository (`owner/repo:path`) or example code, and says what must match. `check-issue` checks that the files exist, the repositories are in `links` and the links are GitHub attachments. `design-fetch.mjs`, run by `go`, downloads attachments and linked files into `.relevo-design/` (excluded from git) inside fixed limits: GitHub domains only, five files, images up to 5 MB by their first bytes, text up to 200 KB, the token sent only to GitHub. `go` adds a scenario "Matches the reference ..." for each reference, which becomes a line of the review checklist, `dev` reproduces it with the project's own tokens and invents no asset, and `qa` checks the code against it. The new setting `design.images` (default `false`) controls whether pasted pictures are downloaded and shown to the model, because they may show customer data. A reference that cannot be fetched sends the issue back to its writer.
- **Scripts** that hold the rules `go` must not vary: `preflight`, `issue-hash`, `branch-state`, `spec-ready`, `intent-to-add`, `commit-change` and `next-step`, plus the protected-paths and OpenSpec-command tables they and the tests share.
- **`Allow-paths:` line** (optional) in the issue format: the dependency files a change may touch. The files that control the workflow (`.github/`, `relevo.yml`, `.relevo/`, skills, the project rules file) can never be listed.

- **Platform registry**: `platforms` in `relevo.yml` (stack, folder and targets of each platform); the older `platform: flutter-android` still works as one Flutter platform for Android.
- **Stack profiles** (`stacks/<stack>.md` in the plugin, starting with `flutter`): the commands that verify the code, the generated files left out of the diff, the tools, the targets and the typical bugs, in one file. A repository adds to a profile with `.relevo/stacks/<stack>.md` and replaces a command only with `platforms.<name>.checks`.
- **Extra skills per role** (`dev`, `qa`, `issue`, `review`), resolved from the base branch by `scripts/role-skills.mjs`; a skill with scripts is used only when `skills.allow_scripts` names it. `doctor` lists the skills left out, warns over 20 KB per role and compares each skill with `skills-lock.json`.
- **Documentation**: [Stacks and platforms](docs/stacks.md), in English and Spanish.

### Changed

- **`doctor` no longer fails when no model secret exists**: the cloud cannot build, but a local build can, so it warns. Copy the `go` and queue workflows again to get the pause variable, the credential check and the new report steps.
- **`Depends-on: acme/api#12` is no longer read as issue 12 of this repository.** Until now every `#number` of a `Depends-on:` line was taken as local, which could unblock the wrong issue. Copy the workflows again to get `GH_LINKS_TOKEN` in the gate and the queue.
- **`go` with several platforms** builds the platform the issue names instead of refusing; an issue that does not name a valid platform goes to `needs-spec` with the list of platforms. The decision `platform` and its message of the previous release are gone.
- **`fix` commits through `commit-change.mjs`** (protected paths, scan and the platform folder in one step) instead of staging and scanning by hand.
- **The `go` workflow template** exposes `platform`, `stack` and `path` from the `decide` job, and its setup examples are guarded by the stack (Flutter, Vue, Laravel); copy `relevo-go.yml` again to get them.
- **Agents `dev` and `qa` are generic**: the Flutter text moved to the Flutter profile, and `go` hands them the resolved profile. They do not edit `relevo.yml`, `.relevo/` or `skills-lock.json`, and `qa` rejects a diff that touches them.
- **`qa.rules_from`** accepts a list of files; every listed file is protected. `skills-lock.json` is a protected path.
- **`doctor`** reads the toolchain and the targets from the profile of each platform. The checks `tools.toolchain` and `tools.device-bridge` are now `tools.<tool>` (for example `tools.flutter`) and `tools.target.<platform>.<target>`.
- **`init`** asks for the platforms (name, stack, folder, targets) and writes `platforms`; it can create a commented `.relevo/stacks/<stack>.md`, which it never commits.
- **`go` is hardened**: it checks that the issue text is the one that was approved (hash), refuses protected paths and temporary markers or credentials in what it commits, never touches a branch that already exists (the comment says how to recover, by its content), reads the progress of the build from `openspec instructions apply`, uses only a closed list of OpenSpec commands, and ends every comment with the next step from one table in English and Spanish.
- **Agents `dev` and `qa`** run only `openspec status` and `openspec instructions apply`; QA reviews the diff of the working tree against `origin/<base>`, and on a retry still runs analysis and all tests.
- **Workflow template**: copy `relevo-go.yml` again to get the new wording of the final step (a run can be cut at its turn or cost limit) and the install examples without package scripts.

- **`create` is now `issue`**: `/relevo:create` is gone, with no alias, and `/relevo:issue` replaces it. Without an argument it writes new issues exactly as before; with an issue number it updates the description of an existing one.

### Upgrading from 0.1.0

- Copy the workflow templates again (`relevo-go.yml` and `relevo-queue.yml`) into `.github/workflows/`: they gain the pause variable `RELEVO_CLOUD_GO`, the check for a model credential, the read-only token for linked repositories, the reports of what a run used and the stack-guarded install examples. Running `/relevo:init` again lists what differs from the templates without overwriting anything.
- `relevo.yml` needs no change: every new setting has a default (`platforms` from the older `platform:` line, `links`, `review.autopilot` off, `design.images` false, `limits.building_alert_hours`). `/relevo:init` lists what it would add.
- `/relevo:create` is now `/relevo:issue`.

### Known limits

- Several parts have been exercised by tests and by pieces run for real in a development environment, but not yet on a live team or a real build: a cloud build of an issue in the format v2 or for a Vue or Laravel platform, a real `go --local` run, the Flutter driver flow and the `precheck` and `verify` modes of the review against a real app, the download of a real pasted attachment for a design reference, the circular buffer of a real device, and a review by more than one person. Each is recorded in [pilot findings](docs/pilot-findings.md).
- `review.autopilot` is `off` by default for that reason, and `design.images` is `false` by default because a screenshot can show customer data.
- A backend (Laravel) has no `review` adapter, and the review of iOS is not available yet.

## [0.1.0] - 2026-10-15

The first release. It covers the whole cycle for one person, from an idea to a merged pull request, on a Flutter Android project hosted on GitHub.

### Added

- **Commands**, as a Claude Code plugin named `relevo`: `init`, `doctor`, `think`, `create`, `go`, `review`, `fix`, `ship` and `status`.
- **Agents** `dev` and `qa`: the developer implements a specified change and the QA agent audits it, read-only, against the specification and the project rules.
- **Workflows** to copy into a repository: `go` (a light `decide` job that runs the gates and claims the issue, then a `build` job that runs the agent), the queue, the review events, the review SLA reminder and the daily digest.
- **The issue lifecycle**: eleven labels, hand-off messages in English and Spanish, one message per hand-off, and a work-in-progress limit per person.
- **`relevo.yml`**: one configuration file per repository, validated, with defaults.
- **Documentation that travels in the issue**: the glossary entries and decision records settled while thinking go in a `Documentation` section of the issue, are written by `go` in the same pull request as the feature, and are checked by QA.
- **Security**: issue text treated as data, a closed tool list with no web access for the unattended agent, a `trust` level, a ruleset that keeps the agent on `feature/*` branches, and the verified inputs of the agent runner (see `docs/action-parameters.md`).
- **Verification of the project itself**: acceptance tests that run the real scripts, a structure test for every skill, agent and template, and a CI workflow.
- **Documentation** in English and Spanish, the findings of two pilots in `docs/pilot-findings.md`, and the design and specifications in `openspec/`.

### Known limits

- Only the one-person path has run on GitHub and on a real device. Approval by a second person, the `peer` and `roles` review modes, the review reminder and escalation, the review events and the reviewer selection are covered by tests only. A team that uses them may find problems; they will be corrected in a later release.
- Platform: Android with Flutter. Tracker and Git provider: GitHub.
- Branch protection and rulesets need a public repository or a paid plan on GitHub. Without them, approving and merging are enforced only by the written confirmation that `ship` asks for.
- The plugin works together with tools it does not bundle: the OpenSpec command line, `git`, the GitHub CLI and, for `think`, the skills of OpenSpec and mattpocock/skills. `doctor` reports what is missing and `init` offers to install it.
